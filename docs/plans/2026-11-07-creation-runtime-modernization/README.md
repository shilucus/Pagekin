## 1. 结论与推荐路线

推荐保留 Pagekin 的领域内核、事实源和纸墨阶段界面，以性能基线为共同起点，分支推进等价热路径优化、独立项目运行时/真实工作流驱动，以及单书规划反馈候选。多书工作流并行依赖运行时和持久驱动；单书反馈试点不依赖这两项；授权整书自动化再汇合其所需的规划、跨批候选、授权和人工终验能力。不要重写成 InkOS，也不要用删除切书提示、无限 `Promise.all`、绕过定稿或人工批准来实现提速。

六项需求的判断如下。证据编号见[源码证据索引](evidence-map.md)，多轮独立审查见[审查记录](review-record.md)。

| 用户问题 | 本轮结论 | 对应解决方式 |
| --- | --- | --- |
| 1. 拆书、仿写卡顿/未响应 | 确认存在重复整书读取、重复流式快照处理和同步计算路径；尚未运行复现，不能指定唯一根因 | P0 分段采样及等价热路径优化，必要时隔离纯计算，见第 3 节 |
| 2. 切书必须取消任务 | 单活动租约、单项目数据库、renderer 当前项目校验共同形成限制，不只是提示文案 | P1 项目运行时与视图分离；切换不关库、不撤销后台任务能力，见第 4 节 |
| 3. 不能按意见修改 | 正文已有审修闭环，大纲已有范围重写；缺的是规划阶段一致且不会直接覆盖的反馈候选流程 | P2 目标限定的多轮候选、差异确认和 CAS 采用，见第 6 节 |
| 4. 生成慢，希望并行 | 有串行循环，也有收据、前缀和事实依赖；不能整链并行 | 优先跨书及独立网络任务，有界调度；书内正文和提交保序，见第 5 节 |
| 5. agents/CLI 创作、机器初验、人工终验 | 已有内部 Agent 工具和生产 generation owner，但没有完整入站公共自动化闭环 | 领域 API + CLI/MCP 适配 + task grant + 真实 driver + 独立人审收据，见第 7 节 |
| 6. 吸收 InkOS | 值得借鉴调度、能力入口、版本/反馈与上下文追踪；不能整体迁入 | 按能力适配而非源码搬运，见第 8 节 |

“不影响产出”指保留输入材料、范围、作者事实、输出合同、审修要求、提交与恢复语义，并以确定性与真实模型两层证据检查退化；不承诺随机模型逐字输出相同，也不预先承诺提速倍数。

## 3. 卡顿与等待：先减重复工作，再决定隔离

### 3.1 静态定位与待证假设

| 路径 | 已确认的代码行为 | 仍需运行证据 |
| --- | --- | --- |
| 拆书冻结输入 | `captureImportGenerationContext` 先读取全书 `content_snapshot`，再筛选批次或首尾样本；准入/来源重建可重复触发 [E04] | 调用次数、读取字节、SQL/哈希耗时、RSS |
| renderer 抽样 | global/style 为取代表章节分页搬运整书，两阶段各自扫描 [E05] | IPC 字节、堆占用、GC 与 UI 停顿关联 |
| 流式通知 | 每个可见 delta 通知，owner 同步回读 durable receipt，传累计持久化全文；renderer 去重前先 hash [E06] | 重复 revision、DB/IPC/hash 队列、React 各自成本 |
| 导入解析/落库 | 安全文件读取为异步，之后拆章、计数、哈希和 SQLite 批事务仍同步 [E07] | 哪种规模触发长 main task；不能称读取全为同步 |
| 网络与生成 | embedding、主题检索、导入阶段/批次、工作流步骤有顺序等待；还受 stage/effect receipt 与内部前缀约束 [E08-E10] | 本地准备、排队、服务商首响应/思考/输出、修复、保存占比 |

以上是可证伪假设。未响应也可能与文本规模、native IO、供应商延迟或环境有关，本轮未排除。

### 3.2 第一批等价优化

- 将整书查询改为数据库端精确选择当前范围、首/尾或前 3 后 2 行；保持原排序、短书去重、实际样本、指纹与提示一致。不能把有章号缺口的“前几行”错误改成固定章号。
- renderer 只获取必要元数据和小样本；主进程仍冻结/验证权威正文，不接受 renderer 自报材料可信。
- 先在可信发布端减少相同 durable revision/状态的重复回读和全文发送；诊断单独合并，终态、失败、取消、存储故障与最终 flush 必须及时送达。第一批不改持久化格式，不扩大可丢失尾部窗口，不删除 hash/单调性/身份检查。
- 重连仍以权威完整快照恢复。不能仅凭不可信 revision/hash 跳过完整性校验；未来 delta 协议须另定 base revision、顺序与全量补偿合同。
- 先减重复解析/哈希，再按采样决定把拆章、纯解析、差异计算放入受控 worker。main 保留 grant、路径/大小准入和最终来源/事务检查；不跨线程传 native DB 句柄，不先拆每书全能进程。
- 保留 KB source gate。缩短锁区或重叠 query embedding 前须证明冻结、验证、提交边界不变，不以提速为由删锁。

### 3.3 采样与指标

实施时以隔离虚构固定文本建立小/中/大三档（建议 10/100/1000 章），测 1/2/4 书任务；先测受控响应，再授权测真实模型。记录设备/平台、SHA、语料 hash、模型/参数/Skill、冷/热缓存和完整失败分母。

分段记录 task/run/attempt ID、耗时、字节与计数，不记录正文、提示词、密钥、原始服务商错误体。复用 transport diagnostics；收到响应、思考输出、首个可见正文分别计时。

候选目标，不是实测：交互 p95 <= 100ms；后台不造成持续 > 500ms 的主线程停顿；小批次正文读取量与所选范围而非全书相关；重复 durable revision 不随 delta 数产生同规模全文 IPC。内存以在途/队列有界、完成后释放、相对基线趋势判定，设备硬阈值在基线后确定。

总耗时拆为准备、排队、模型、解析、保存、投影/后处理，报告 p50/p95、失败率、429、物理请求与实际 usage。模型思考/网络等待不是 UI 卡死，增加刷新频率不会加快模型。

## 4. 多书运行时：视图不再拥有任务

### 4.1 当前限制为何必要

切换前取消并等待原项目任务 [E01]；打开新项目先关闭全局 `projectDb` [E02]；`ProjectAccessService` 只保存一个活动租约 [E03]；执行器与等待 Promise 在 renderer 内，启动及步骤前后绑定 UI 当前作品 [E11]。generation owner 虽按 DB 有 Map，准入仍依赖唯一当前项目，关库时暂停并移除 owner。

仅改多任务数组、允许多租约、开多个页面或删提示均不充分；异步时临时切换全局 `currentProject` 更会制造串书写入风险。

### 4.2 推荐目标结构

```text
纸墨 UI / CLI / 入站 MCP 适配器
                |
       领域命令 API + 授权/幂等准入
                |
       单一本机 RuntimeHost / Broker
          |                     |
   全局公平调度器         任务/步骤持久化驱动
          |                     |
   ProjectRuntime A       ProjectRuntime B
   DB/owner/KB/epoch      DB/owner/KB/epoch
   资源锁/提交/outbox     资源锁/提交/outbox
          |                     |
       原有领域 writer、generation owner 与收据合同
```

图是逻辑职责，不强制全部新建 class/服务。复用当前 owner、repository 和 generation ledger，只在真实边界需要时新增职责。

每书运行时显式持有 `projectId + canonicalRoot + databaseIdentity + executionEpoch`、任务能力、DB/KB/owner 与关闭状态；UI 的 `activeViewProject` 仅决定展示。长异步在入口捕获运行时，整个纵向调用链不再借用后续全局当前项目。

首批限定一个完整生产工作流，建议“已有规划 -> 批量草稿 -> 机器初验 -> 待作者验收”。将步骤驱动、等待决策、取消、恢复迁到主进程或受控宿主。不能仅搬 provider 网络调用，仍靠隐藏组件或 Zustand Promise 驱动后续步骤。

### 4.3 授权与生命周期

| 动作 | 目标行为与边界 |
| --- | --- |
| 切换查看 A -> B | 只改视图订阅；A 保留任务能力和 DB。B 的缓冲独立，A 结果不覆盖 B |
| 同项目再次查看 | 连接已有 runtime，不机械 reopen/fence；真正重开/接管发新 epoch，旧能力失效 |
| 停止某任务 | 阻止后续 dispatch，等待在途请求安全收尾，保留候选与 unknown |
| 关闭/卸载项目 | 与切换区分；暂停/取消、flush、等待后释放，不先关 DB 再等异步写入 |
| 退出应用 | 首期保留关闭保护，结束/暂停后退出；不声称进程退出后仍能跑，独立 host 后续交付 |
| 崩溃/重启/接管 | 从持久 ledger/receipt 对账，发新 fencing epoch；不沿用旧窗口租约，不自动重发未知请求 |
| 删除/恢复/迁移/备份 | 对对应书建立维护屏障并协调所有 owner；活跃写入时不移动/删除目录，不只备份 DB 主文件 |

旧 UI 租约不自动升级后台能力。主进程在 task grant 下签发限定项目、动作、范围与生命周期的执行能力；旧 renderer IPC 仍按旧租约失败关闭。多能力与单活动视图的关系须经新 ADR、版本化 IPC 和端到端测试明确。

同一 canonical project 写 owner 必须唯一。第一阶段所有 UI/CLI 连同一个 broker；未来 headless/desktop 竞争同书时，用 OS 级排他与持久 fencing 防双 owner，不能只靠进程 Map 或 SQLite WAL。

### 4.4 新旧入口共存的最低门槛

“首迁一条工作流”不意味着基础生命周期只迁这条调用链。项目打开/关闭、DB 生命周期、当前作品编辑、定稿及维护入口必须先有统一的 runtime 路由或明确拒绝；旧 project:open 不能继续用全局 initProjectDatabase 关掉后台 A [E02/E26]。

| 入口类别 | 共存规则 |
| --- | --- |
| 已 context 化的 driver/领域写入 | 经同一 broker 路由到捕获的 runtime，允许按资源策略后台运行 |
| 打开/查看/关闭、DB 生命周期和基础编辑 | 优先统一入口；兼容层必须显式选 runtime，不临时切全局身份 |
| 未迁移且依赖当前项目的旧工作流 | 保留既有取消/等待及切换保护；与新后台模式无法安全共存时拒绝启动，不暗称支持后台 |
| 未迁移的直接 DB/定稿/维护入口 | 活跃新 runtime 时拒绝或经已审兼容适配路由；禁止绕过锁/维护屏障 |

按工作流发布迁移清单与能力资格，不能统一移除所有切书保护。验收包含“后台 A + 旧入口开 B/关库/定稿/备份”，以及新旧工作流同时存在时的切换决策；不得关错库或让旧链借用新会话。

### 4.5 grant、owner 与撤权的线性化

execution epoch 只围栏 owner；grant revision 独立控制授权动作/范围、到期、缩权和撤销。最小 grant/撤权语义属于 P1，不等到 P3；P3 再增加创作策略和机器决策授权。

每次出队/dispatch 和领域 effect 提交重验 grant、revision、epoch 与维护状态。撤销与提交在同一项目串行/事务准入点裁决：提交先完成的事实与收据保留；撤销先完成则禁止新正式 effect。已 dispatch 请求仍结算账本，结果最多按预授的系统清理权限保存隔离候选/诊断，不代表继续采用；没有该权限时保留现存 durable 数据，不为补尾新增越权写入。清理只能收敛旧请求，不能启动模型或新领域操作。

历史读取权限单独核定；撤权不能靠幂等回放重新触发发布、合并或其他 effect。批准后到定稿前也重验当前执行/批准能力，撤权不删除历史批准证据。验收覆盖撤权在排队、dispatch、返回、事务提交、批准后各时点，以及维护/接管与提交竞争。

## 5. 安全并行与速度提升

### 5.1 并行矩阵

| 工作 | 推荐策略 | 必须保留 |
| --- | --- | --- |
| A/B 书模型任务 | runtime 隔离后优先跨书并行 | 各书授权、来源、资源键、收据、错误归属 |
| 多主题 query embedding/检索 | 输入独立部分有界重叠，按原主题顺序装配 | 原材料覆盖、每主题错误语义、KB gate |
| 文档/分块 embedding | 有界池，按原 chunk index 归位，背压限制在途正文 | 数量/维度/指纹、一次有效提交、取消 |
| global 与 style | 暂保顺序；独立冻结源明确后再并行候选 | 当前 stage/effect receipt，先改合同 |
| 不同外层蓝图批次 | 后续探索独立快照生成候选 + 顺序来源检查/采用 | core/角色同步变化不让后批悄悄用过时输入 |
| 单批拆分/修复/续写 | 顺序执行 | validatedPrefix 与 attempt 身份，不并发重试 |
| 正文 N/N+1 章 | 保持依赖顺序，可与另一书并行 | 前章上下文、候选/定稿身份、连续性来源 |
| 同章 UI/CLI 修订/合并/定稿 | 主进程共享资源准入，冲突排队或返回冲突 | 源 hash/CAS、作者缓冲、唯一领域 writer |
| DB/outbox/共享角色派生 | 短事务、项目/资源级协调 | 事务顺序、字段来源所有权、投影失败不回滚事实 |

导入既要求阶段匹配，也要求此前 slot 的 effect committed [E08]；单命令 runtime 拒绝嵌套/并发 [E09]。新 DAG 必须改主进程准入、步骤状态、恢复和 scope 证据，不只并发调用旧 Command。

蓝图批内前缀不是全书前批内容。外层批潜在独立，不证明当前合同允许；角色同步和 core 版本变化必须纳入依赖图。

### 5.2 调度政策

- 限制全局、服务商/凭据主体、模型和项目在途请求，按 opaque credential reference 分组，不把 API key 放任务、事件或参数。
- 初始并发建议从 2 压测，不固化永久上限；按吞吐、429、延迟、内存与质量放开。任务/书间轮转，前台交互保留资源，避免长书占满槽。
- 队列有界，不持有长 DB 事务排队；资源获取顺序固定，阻塞可取消。先做网络并发，不先平行化全部 CPU/native。
- 取得全部资源/传输槽后，真正 dispatch 前重验 grant/revision、runtime epoch/关闭/维护、模型租约、来源 fingerprint、取消/阶段与根预算，再原子 reserve/mark dispatch；期间若 await，返回后重验。过期未派发节点进入明确冲突/待决策，不静默重冻来源；最终采用 CAS 不能替代发出前准入 [E27]。
- 冲突判定下沉主进程，复用 read/write resource claims，UI/CLI/Agent 不各设互不相知的锁。
- 每次物理请求仍 reserve -> dispatch-marked -> settle，保留同根次数和活动时长。时长按现行根活跃区间，不累加并行子请求耗时，也不借队列/暂停清零刹车。
- 取消阻止未派发节点；在途取消不代表供应商未执行。结果不明保留 unknown，不换 nonce；429/失败重试沿现有已知终态合同，不加通用盲重试。
- 分开逻辑任务终态、本地 transport 生命周期、远端结果确定性。当前取消的 Promise.race 可先于 provider promise 结束 [E25]；传输 permit 至少持有到本地请求真正结束/确认关闭，不能按 task cancelled/unknown 立即补位。对无法收敛的遗留请求设有界隔离与受影响通道停发/人工处理策略，不能无限持槽或释放补位；本地关闭仍不证明远端已停止，未知远端额度按明确策略保守限制，不承诺严格远端并发证明。
- 降并发到 1 是运行策略回退，不撤销已提交事实、不抹迁移、不重发未知任务。

embedding 并发必须保留文档级 outcomes：完整且通过校验的向量集、现有允许的整文档 FTS-only，或硬失败。普通网络失败与 EmbeddingResponseValidationError 的既有差别不变 [E28]；不新增部分成功向量投影。停止派发后吸收在途结果，提交再验 authority；稳定文档 ID、原文与 effect receipt 一致，sibling 完成不能隐式提交。

等价并发按原batch序号归并缓冲结果，以原串行路径首先遇到的失败决定文档outcome，不按返回先后或“任意validation error优先”。低序号网络失败、高序号非法向量时仍是原有FTS-only；反序则硬失败，均不提交后续向量；所有batch成功后仍做整体校验。高序号sibling只收敛/诊断，实际已发生请求如实计数。若要更严格新裁决规则，必须另列行为变更，不再称等价优化。

### 5.3 品质不退化的门

等价热路径比较受控输入下的样本、冻结提示、字段、章范围、收据和恢复。改变上下文/顺序/候选依赖的优化，另做同模型/参数/Skill/语料的配对质量评估，保留失败与未运行分母。

比较文风、事实/角色一致性、必要事件、来源、重复、节奏、范围外变动和补修调用。采用[现行质量协议](../../research/novel-quality-modernization/quality-protocol.md)，不发明文学 PASS，不以 mock/JSON 解析代替文学评审。性能比较与正式资格分开，不改写既有正式采样分母。

## 6. 统一反馈迭代，不重建正文审修

### 6.1 当前能力与缺口

| 目标 | 已有能力 | 本次建议补齐 |
| --- | --- | --- |
| 设定/核心大纲 | 人工编辑、单字段/整体 AI 补全；扩写保留原文 [E12] | 独立按反馈修订模式，不强制保留原句，生成只产候选 |
| 前提/世界观 | 编辑、重新生成、逐节作者指导；成功正式提交 [E13] | 当前底稿显式纳入修订输入，比较后采用，不冒充重生为保守修订 |
| 情节大纲 | 指定章范围重写、范围外原文保留、CAS 保存 [E14] | 复用范围 writer，加候选、采用前 diff、可恢复旧快照 |
| 角色名单 | 结构化编辑、提议/确认；已有蓝图禁止整批重生 | 字段反馈与 character proposal，不删稳定 ID/门禁 |
| 蓝图 | 编辑、补空缺/覆盖/范围生成、内部 Agent 字段提议 [E15/E16] | 单章/指定字段修订；不能借会删范围外内容的 full 覆盖 |
| 正文 | 直接修稿、意见/指导编辑、确认后修稿、逐块合并/复验 [E17] | 复用内核，补入口一致性、任务/验收衔接，不造第二套审修 |
| 历史/恢复 | 中断候选、编辑恢复、正文版本/重开定稿 | 恢复不等于通用迭代史；规划采用历史须核定持久化，不能承诺零 schema 变更 |

正文合并会就地更新草稿，不能宣称当前每轮自动产生完整不可变正文版本。规划历史也不应硬塞正文 revisions 表。

### 6.2 交互语义与提交协议

```text
明确目标/底稿 -> 反馈/不可改约束 -> 冻结来源/模型/Skill
 -> 独立候选 -> 范围/完整性检查 -> 差异选择/手改
 -> 主进程校验最终载荷/CAS 采用 -> 领域收据 -> 下游影响提示
```

1. 目标限定为字段、架构节、大纲章范围、蓝图字段或正文稿件。先处理该目标未保存缓冲，不能默默用旧持久稿覆盖正在编辑的内容。
2. 候选分开 adoptionBase（正式目标/预期 hash或revision/范围/上游refs）和 generationParent（本轮实际输入的正式稿或不可变候选及hash），并绑定反馈/约束/scope/run/artifact/模型/Skill。F0 -> C1 -> C2 未采用时，C2记录父C1，但采用仍对F0做CAS；不把C1 hash与正式F0错比，也不抹掉真实候选来源。
3. 复用配置/蓝图 proposal diff、差异库与合并语义，按目标薄适配，不先造能写所有表的万能 revision framework。
4. 采用前主进程对最终选择/手改载荷按目标现有合同重验，再与来源/范围CAS在同一提交边界完成，走对应writer、保存旧快照和收据。不合法的章集合/身份引用闭包零正式写入，不自动补用户未选字段；不把结构限制强套自由正文。幂等绑定候选版本、实际载荷hash、范围、决定来源；同键异载荷拒绝，不把renderer generated标记当授权 [E29]。
5. 底稿/上游变化，候选可读/复制但不能直接覆盖，不静默 rebase、换模型或重发。明确选择新底稿后才开新修订。
6. 下游影响列既存计划/草稿/定稿、角色派生和线索，不保证查出全部语义矛盾、不自动改后续。定稿修改复用重开稿/唯一 writer/outbox；当前审稿不检查后续定稿全文的限制继续披露。

全量或局部采用后，正式目标已改变，依赖旧 adoptionBase 的其余候选/后继均转冲突、只读保留；不能沿旧基线自动再提交。建立新基线需明确选择与新反馈操作。重启保持两类来源可追溯；部分采用不能自动 rebase 剩余候选。

### 6.3 可见差异的需求证据与设计缺口

本轮不改界面。下表只定义功能差异，不锁按钮文案、布局、颜色或尺寸。

| 新增/改变的输出 | 需求来源 | 可复用依据 | 尚缺设计证据 |
| --- | --- | --- | --- |
| 切书仍显示任务归属/后台状态 | 用户问题 2/4 | ADR-0021 流程与按需侧页 | 全局/项目边界、切换/退出/冲突、桌面视口 |
| 规划反馈输入/候选状态 | 用户问题 3 | 正文审修、作者指导、proposal diff | 各对象入口、空/忙/失败态、最终文案 |
| 差异/部分采用/过期来源/影响 | 问题 3 与事实保护 | MergeView/DomainProposalDiff/ConfigImpactPreview | 字段/范围、手改冲突的完整设计 |

## 7. API、CLI、Skills 与人机验收

### 7.1 两档交付，避免只登记不执行

第一档 desktop 在线 broker：CLI/Agent 连正在运行的 host，生产 WorkflowDriver 真正执行；切书不影响任务，整个进程退出后不承诺继续。

第二档才是生产 headless：抽出与 window/Zustand/导航解耦的 runtime/driver，desktop/headless 二选一持同书写能力。必须有启动/健康/停止、单 owner/接管、凭据安全、native 与三目标检查。verify:drive、测试 harness、隐藏窗口自动点击不能充当生产 headless。

现有 MCP 是出站客户端，不是入站 server [E18]。入站 MCP 只是领域 API 适配层，不能暴露全部 preload IPC、任意文件或 SQL。

### 7.2 默认候选与显式任务授权

| 模式 | 可自动执行 | 禁止/限制 |
| --- | --- | --- |
| 默认 candidate-only | 获准作品/范围内新草稿、机器审稿、修订候选、报告 | 不覆盖作者规划、不自动合并已有正文、不定稿；不宣称从零无限写整书 |
| 显式 task-grant | 作者发布时批准作品集合、章范围、空位/可写字段、模型/已装 Skill、修复策略/次数；中间步骤自动提交并产收据 | 不扩目标、不覆盖未授权内容、不安装/执行脚本、不改凭据、不删除/最终定稿；来源变化转待决策 |

一次授权可覆盖中间规划采用，避免逐步弹确认；来源记任务授权生成/机器决策，不标作者逐项审阅。当前 human-confirmed-review 有真实人审来源 [E19]；自动选意见不能伪造此类型或填 confirmed=true。

无人逐步干预的机器修订须增加独立可审计的 automation decision/grant，经新合同及必要迁移复用修订逻辑；不绕过人审字段、不废弃原人工流程。最终批准单独认证、收据绑定实际交付 hash。

现有 draft_review 每批最多 10 章，普通后续写作要求前章定稿/关键后处理 [E20]。长篇跨批候选链须扩展显式依赖/恢复，不能冒充 finalized、不能用 auto_finalize 偷渡终验。第一版只交付已支持范围，全书无人值守以跨批候选通过为独立完成条件。

跨批前驱被改稿、重选、局部采用或替换后，依赖旧候选hash的后继转conflict并只读保留；单纯把前驱升为相同正文的正式稿也不悄悄改refs，只有预先声明并验证的候选->定稿收据映射可算预期转换。受影响后继要重新建立依赖/必要人审，不换版本掩盖原失败基线。

不优先新造整书副本/overlay，避免第二事实源、身份重映射/合并。先复用真实稿件/规划 writer 和 task ledger；表达不了授权中间材料时，再另立工作副本提案。

### 7.3 领域 API 草案

以下不是已实现或冻结的公共接口，字段/命令名待详细契约审查。

| 能力 | 语义与最小收据 |
| --- | --- |
| projects.authorized-list | 只列获准作品必要元数据，不扫描/返回任意根 |
| tasks.submit | 校验 grant、目标、幂等键、来源；返 taskId/受理/冻结范围，不代表完成 |
| tasks.read/events/wait | 真实步骤、请求、候选、领域收据；事件序号续读，默认无正文/秘密 |
| tasks.pause/cancel/resume | 能力约束、恢复对账来源/epoch，不新 nonce 重抽 unknown |
| artifacts.read | 授权读指定 artifact/version/hash，区分候选/正式事实 |
| proposals.prepare/accept | 字段/范围候选和 CAS，accept 需对应人审或 task-grant |
| acceptance.prepare | 从实际产物构建不可变交付 manifest/初验报告，冻结 hash |
| acceptance.approve/reject | 仅人审作用域，批准所见 manifest；幂等，改产物不能复用旧批准 |

服务端签 capability/run/attempt/artifact/commit receipt，客户端不能自报已确认。参数执行运行时 schema/白名单、范围/大小/路径检查，TypeScript 不等于校验。秘密留 host，不经 stdout/参数/Skill/MCP 日志。

优先同用户 ACL 保护的 named pipe/Unix socket。loopback HTTP 仍需认证、Host/Origin、重放与令牌生命周期；localhost 不等于授权。首期不做公网、多用户、任意脚本或新秘密存储系统。

CLI 至少含 submit、连接实际执行的 run --wait、wait/events、pause/cancel/resume、artifact inspect、acceptance prepare/approve/reject，以及稳定 JSON/可区分退出状态。普通 task token 不得升级人审。Agent 自带模型生成也只能导入有来源候选，再走共同校验/采用，不能直写事实。

幂等作用域绑定项目/调用者/grant/命令种类/key与规范化payload hash；同键异载荷拒绝，不跨client/grant串用。保留期至少覆盖任务可恢复期和关联effect生命周期；超过窗口只可用新明确操作，不自动重发旧未知操作。撤权后的受控receipt读取不产生新effect。

### 7.4 端到端流程

```text
作者发任务/task-grant -> host 冻结范围/来源/模型/Skill/策略
 -> 书间公平并行、书内依赖保序 -> 授权规划/草稿/机器审修
 -> 机器初验：机械检查 + AI 语义意见 + 未核实项
 -> awaiting-human-acceptance，交付精确版本 manifest
 -> 作者 approve/reject -> 既有定稿事务，投影/后处理分别报告
```

机器初验分 execution（请求/保存/投影）、scope（越界变化）、quality（语义/文学意见）；缺证据标 unavailable/待核实，不以语义失败掩盖执行失败，不以引文定位代替语义正确。

automation Skill 说明 API、scope、等待、收据、恢复、初验/停止条件，不是权限载体，不持秘密、不执行脚本、不写 DB。阶段写作 Skill 仍按 ADR-0015；二者分开，复用现有冻结机制，不造通用 Skill 平台。

### 7.5 恢复与真实终点

task ledger 保存 grant/来源/模型/Skill、步骤版本、owner/epoch、attempt/effect 引用、决定来源与交付 manifest；链接现有收据，不另记矛盾成功。跨书总览为可重建聚合，不是第二事实数据库。

至少一次驱动 + 幂等提交，不承诺模型网络 exactly-once。回包丢失查领域收据；unknown 不自动重发；迟到结果不跨书采用。定稿提交、发布、后处理、交付是不同状态，投影失败不回滚事实也不报全完成。

人审 manifest 不是新的定稿 writer。批准后由现有 FinalizationRepository 对精确稿件逐章提交；多章不宣称全有或全无。部分定稿、待发布/后处理失败须可读可恢复，不能重复生成填补收据缺口。

### 7.6 首个 driver 的步骤对账合同

稳定 stepId/commandId 在执行前持久化，不能每次恢复重新UUID。每种步骤在P1-B详细契约列 effect owner、幂等键、来源CAS、receipt查询和恢复状态；模型attempt幂等不能代替所有非模型effect。

| 步骤 | effect与恢复要求 |
| --- | --- |
| 模型生成 | 原run/invocation/requestHash与attempt收据；reserved/dispatch-marked/unknown分别处理，不重抽 |
| 草稿保存 | draft effect及稳定commandId，校验目标/依赖；查到已提交即回放，不新建重复版本 |
| 规划/候选采用 | 对应领域writer、adoptionBase与最终payload hash；已采用回放，不再覆盖当前值 |
| 机器意见选择/修订候选 | 独立automation decision与源报告/正文hash，不伪造人审；候选生成/保存分开对账 |
| 交付/最终批准 | immutable manifest、独立批准nonce/收据和权限；状态回放不额外定稿 |
| 定稿/投影/后处理 | 唯一finalization writer与既有outbox/effect收据；只推进未完成项，不重做已提交事实 |

优先把step的effect引用与领域effect同项目事务落盘。不能共事务时必须有独立可查稳定commandId/receipt，禁止“重跑看看是否已保存”。受理未开始可重入；已dispatch未知先对账；effect已提交只补step引用；等待决策不自动approve；终结只读回放。断点测试必须插在每次领域提交后、ledger更新前，而非只测provider中断。

### 7.7 人工批准与逐章提交协议

威胁模型：防普通automation客户端越权/误用，不声称抵抗同OS账户已完全控制应用或窃取进程凭据的恶意程序，也不声称技术上证明真人身份。同用户ACL只限制用户边界，不能证明作者亲自批准。

默认task/CLI/MCP凭据无法申请、读取或签发人审capability。只在可信UI明确作者动作，或另行确认的可信人工渠道，签发短期、限manifest hash/nonce的批准操作；CLI approve默认仅能消费该次经确认的操作，不能自签scope。机器调用同一命令不获得批准。未完成可信渠道设计前，不开放公共approve写入口。

manifest绑定项目身份/目标范围、draftId/version/body hash/预期状态、重开来源/被替换权威定稿、必要上游refs、机器报告/决定及允许的顺序状态转换。批准后冻结该交付，不再接受原交付上的自动修订；改稿产生新manifest，原批准不批准新版本。拒绝/撤销、nonce消费与幂等重放独立核验，重放不再执行effect。

每章在同一事务核对当前授权/批准receipt、manifest项、目标hash/状态/重开关系/依赖与唯一effect，再由既有writer提交。批准时检查不能代替提交时检查 [E30]。UI本地未保存改动须在批准前处理，不能因DB hash未变就把作者不再认可的快照提交。

批准后采用“封存交付目标 + 显式解封编辑”语义，不让后台猜测未保存缓冲。批准前与所有绑定目标的编辑器完成revision握手：按既有保护处理脏缓冲，同步进入只读封存后才确认；握手中revision变化、窗口断连或无法证明缓冲已处理，保持待决，不自动丢弃/批准。封存revision/manifest记录于host，逐章事务核对；普通API/编辑入口不得改封存内容，只有本manifest批准的定稿状态转换按原writer执行。

作者要继续改封存目标，先向host申请解封，并与逐章提交共用串行屏障：解封先赢则撤销受影响未提交项的批准、发新编辑能力后才允许输入；提交先赢则原快照已定稿，按ADR-0024重开修改，不把新输入写回已定稿。不得在一次SQL事务中await编辑器握手。任何异常迟到本地缓冲仍按ADR-0003保留为显式冲突，不清dirty、不误称其已定稿；窗口关闭/重连须对账封存和已提交receipt，不自动恢复旧编辑权限。此处定义功能状态，具体只读/解封交互仍须设计确认。

多章采用固定顺序与逐项receipt：已提交项保持事实，未提交项若被编辑/删除/恢复/另一次定稿或依赖变化则停止受影响后继、保留待决manifest。由本次提交产生的预期定稿/后处理转换只能按manifest声明映射验证；不把所有版本变化一律忽略，也不把所有变化都误判冲突。恢复只推进receipt证明未提交且仍获批准的项；内容或非预期依赖变更须重新批准。后处理未达现行依赖条件，后继仍暂停，不能以整批批准跳过。

短期客户端批准操作能力与持久批准收据是两类对象：前者到期不抹历史、不重做已提交项；后者不是永久执行权。恢复未提交项须有当前执行权限、仍有效/未撤销的批准及目标封存，旧客户端token不能续办；缺条件进入待作者决定。跨书撤权逐项目出具围栏结果，未全覆盖不得报告全部完成；不承诺跨书数据库原子撤销。

### 7.8 原项目重启与便携新副本恢复分开

7.5-7.7的继续执行只适用于身份/来源有效的原项目故障恢复，不适用于[B01新副本恢复](../novel-quality-program-v3-2026-09-13/specs/B01.md)。新任务持久化必须同时接入现有便携字段策略、历史投影与运行冻结合同 [E31]，不能等到自动化完成后再补备份支持。

- 在新增字段/表落地前，为ledger、step/effect引用、grant/revision、capability、manifest、批准/封存、候选历史逐字段签署“保留可读内容、脱敏不可重放历史、排除机器权限/秘密”的处置。未知表/字段按现有schema门禁拒绝归档/恢复，不默认整表复制或丢弃；迁移与便携格式由各自唯一owner协调。
- 新副本有新projectId/epoch；旧grant、能力、批准执行权、nonce与编辑封存能力不转移。旧已受理/暂停/等待批准步骤、unknown、import/outbox和批准记录只按允许字段保留为nonReplayable历史；启动不dispatch、不自动定稿、不释放或重发旧unknown，也不把旧封存变成新项目持续写锁。
- 保留作者原文、权威定稿、合格可读派生、候选及必要历史，不以安全为由全量丢弃或全部标stale。排除秘密的混合收据只保留允许投影及其hash，不夹带原排除字段的digest/MAC；可读authority转移不授执行权。新副本继续创作须新授权、重建来源/lineage；采用旧候选重新校验，最终定稿重新生成manifest并经新的人审批准。
- 验收区分同项目崩溃恢复与新副本恢复，包含部分定稿/待投影、等待批准、在途unknown、未分类新字段和跨profile恢复；不得以同项目恢复通过代替B01新副本证据。

第一轮审查追加的必测反例：

- provider忽略abort、迟到resolve/reject、反复取消再提交，断言实际transport在途/遗留额度受控、迟到不能写错书。
- 排队取得最后一个槽前改源/撤权/重开/暂停/维护；每个effect提交临界点撤权；旧入口开B/关库不能破坏后台A。
- embedding乱序、单批网络失败、非法JSON/维度、取消/恢复，保持整文档向量/FTS-only/硬失败语义及准确请求分母。
- embedding低序号普通失败/高序号validation error及反序，交换完成时序，outcome/收据与原串行裁决一致，不提交高序号部分向量。
- F0 -> C1 -> C2未采用、直接采用C2、期间F0变F1、局部采用后旧候选失效；手改章号重复/缺失/越界、身份引用不闭合、同键不同选择均零错误正式写入。
- 每种领域提交后/ledger更新前崩溃；已知可恢复操作保留原baseline，不能借最新内容掩盖原失败。unknown仍不重发。
- automation客户端无法签发批准；批准后编辑/撤权、逐章提交后前驱或后继变化、部分成功恢复，只继续获准且来源仍有效项。
- 批准握手中输入、批准后未保存输入/解封、提交中输入、窗口关闭/重连和客户端能力到期：只读封存/解封与commit按同一屏障裁决，迟到缓冲保留冲突，已提交项不重做。
- 相同持久快照分别在原项目崩溃重启与B01新副本恢复：原项目按当前权限/收据对账，新副本不得继续旧step、批准或outbox；unknown只读保留，新授权/显式候选采用走新lineage，未知新字段阻断而非漏带。

测试入口见 [evidence-map](evidence-map.md#后续验证入口只读未执行)。实施时再核定命令、副作用、隔离目录和恢复。pnpm test、typecheck、test:browser、verify:drive 仅入口，不是本轮已授权/已执行；模型、凭据、用户作品、安装包、远端发布分别确认。

## 11. 待确认项与停止边界

1. 可见设计：后台任务/关闭退出、各规划修订、人机验收的布局/文案，本轮无精确设计证据。
2. 授权政策：task grant 采用哪些规划/是否仅空位、机器修复几轮；最终由作者。agents 协助不等于无限写入。
3. 首个纵向工作流：建议已有规划的批量候选；完整拆书/仿写由P1-D独立交付，多批整书、从零规划分别列完成条件，不一开始迁全仓。
4. 运行缺口：无本机曲线/问题复现、供应商额度/429分布、品质不退化、headless/native证据；方案/团队一致不等于验收。
5. 新ADR、IPC/API、持久化/迁移、入站安全须逐包审查授权。本方案进入详细设计，不直接批准生产改造/发布/许可移植。
