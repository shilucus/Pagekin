# ADR-0070: Foreground Reference Knowledge Issuance

Date: 2026-11-13. Status: accepted for the foreground knowledge-only composition increment.

Sources: [F2 sections4.3-4.5/7.5](../plans/2026-11-07-creation-runtime-modernization/README.md), [ADR-0039](0039-reference-import-grant-history.md), [ADR-0068](0068-reference-knowledge-grant-admission.md), [ADR-0069](0069-reference-embedding-dispatch-barrier.md) and the existing explicit ImportNovelDialog launch/resume action. This does not accept the full deconstruction/imitation migration or background execution.

## Issuance And Inputs

Only the existing explicit execute-import/continue launch action prepares a new knowledge issuance. A closed versioned IPC request carries a fresh operation UUID, existing reference run and renderer workflow execution-owner UUID, never a caller-asserted author-action flag, request hash, model configuration, credential or admission. Main validates the current project view and actual WebContents object, reads the existing immutable manifest and selects/copies the actual embedding inputs once. Protocol, provider, endpoint, model name, credential and normalized embedding options stay in private main memory. An unconfigured embedding selection retains the existing FTS-only behavior; this stage does not add model fallback or new embedding policy.

The existing documented OpenAI-compatible legacy protocol fallback is materialized as the actual openai literal rather than an unsafe TypeScript cast of undefined. Anthropic remains ineligible and Gemini remains explicit. The existing embedding-space mismatch/reindex-required guard is retained: an old index accidentally identified by an undefined protocol is not silently relabeled or migrated.

Preparation synchronously uses the existing ImportRunRepository.startOrResume and grant writer in one native transaction, freezing that exact execution owner/epoch and registered runtime/root/database/native identity/epoch. This is the renderer workflow's existing lease, not a second executor, whole-stage owner or handoff. The request binding includes the immutable scope and safe model/input identity; a hash alone is not the actual input capsule. No native transaction spans an await. Publication follows successful commit with no asynchronous gap. Same-operation replay requires the same live private sender issuance, exact run/owner and valid captured lease; lost private state cannot reconstruct it.

A new explicit launch can choose current embedding inputs for a new grant/key after the existing lease acquisition rejects a different live owner and all earlier admitted chapter calls have drained. Prior grant revocation and new issuance are atomic. Supersession does not invoke the old cancellation finalizer against a new execution. Old grant/receipt/dispatch histories remain; neither new authorization nor a new model changes the existing prepared/unknown no-resend barrier.

## Execution And Final Effects

Automatic stage resume consumes the private issuance and only validates/renews the captured owner/epoch. It cannot call startOrResume, clear cancel_requested, acquire a new epoch or resurrect a revoked/cancelled run. The old db start-resume and KB reference import channels reject runs with any persisted reference grant history, including revoked grants and lost capsules. Author-manuscript and genuinely unmanaged legacy runs retain their existing contracts.

Every admitted chapter uses the captured runtime resources and issued ReferenceImportAdmission with the frozen embedding inputs. Existing source/execution/integrity checks remain. The main boundary holds an outer runtime work lease through KB loading/import, the final post-await ImportRunRepository.commitReferenceImportReceipt inside admission.withTransaction, and all synchronous cancellation cleanup. A committed KB document is not rolled back when a later revoke forbids the separate run receipt; that document remains a durable fact, not a successful run receipt.

Revocation first invalidates the private lifecycle consumed by genuine admission checks, then revokes the durable grant and requests cancellation through the existing run writer for the captured execution. A failed durable revoke cannot authorize further dispatch or effects through a still-active database row. In knowledge, boundary cancellation waits for all admitted physical chapter calls to finish; the last caller performs full grant-and-cancellation quiescence before releasing the last outer work lease. Zero-in-flight knowledge or never-resumed launch cancellation is synchronous. Unresolved cleanup retains its exact locally revoked issuance for a later close attempt, without retaining usable credentials after drain; only successful quiescence clears it. A cleanup failure cannot replace the safe primary error, including a structured failed KB result. Only safe diagnostic codes are retained together; arbitrary provider or storage messages do not cross this boundary.

Sender destruction and runtime close request use that same main-only knowledge quiescence path without relying on another renderer call. Later global/style/blueprint operations are not physical flights owned by this authority: their existing orchestrator/owner retains boundary cancellation and draining; zero admitted KB calls is not proof those generation requests are idle. Cleanup cannot cancel a superseding epoch. Completion marks the grant completed only after the existing full run is actually completed, never at the end of knowledge alone.

Each private issuance owns its exact sender-destruction listener. Successful terminal cleanup removes only that listener after admitted work drains; same-operation replay does not register another one. In-flight or unresolved cleanup retains the existing issuance and recovery protection. Project close must not leave completed issuance callbacks retaining an old authority/runtime on a still-live sender.

## Visible Outputs And Qualification

No layout, control, progress stage, success text or resource is added. Existing execute/continue buttons remain the explicit action. During the new asynchronous preparation, continue uses the existing importing busy/disabled state and existing loading output; its failure uses the existing error area. Closing, unmounting or replacing that pending launch invalidates it, so a late response only revokes its own issuance and cannot start a workflow or close a newly opened dialog. These state differences map the existing launch/resume controls to F2 authorization, cancellation and recovery requirements; they do not introduce a new control or copy. Main-boundary authorization failures use the existing locale-specific integrity failure template. Author-manuscript behavior is unchanged. Both locale/browser-state regressions and the production error-mapping gate are required; fixture error text alone is not end-to-end localization evidence.

No persistent field/migration, imported source adoption, global/style/blueprint writer, headless entrance, budget amount or concurrency limit is added. novel_import stays background-unqualified. This process-local capsule does not survive restart, restore, sender replacement or runtime replacement; a new explicit action must issue a new grant, and unknown requests still cannot be resent. Complete IMPORT-001/002 and SCHED-001/002, durable whole-driver recovery, model quality and platform qualification remain incomplete.
